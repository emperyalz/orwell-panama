This also removes the prior dead path that compared `effectiveFrom===to` (never true for the default selection because `to` defaults to the empty string `''`).
- `src/components/reference/IntelligenceWorkspace.tsx:43` — `selectedRangeGap` is true only when: a single person is selected, a platform is selected, the resolved bounds are valid (`effectiveFrom<=effectiveTo`), **and** an account for that exact person+platform exists in `data.accounts`, **and** `data.buckets` has no entry for that person+platform with `count>0` whose `month` falls in `[effectiveFrom, effectiveTo]`, **and** `data.examples` has no post for that person+platform whose UTC month falls in `[effectiveFrom, effectiveTo]`. This is the "selected person/platform with no archived bucket/example in the selected month/range despite the account existing" case from the acceptance criteria, and it is **range-aware**: it fires for an explicit same-month `from/to`, an implicit-end single month (`to` empty, resolved to the latest archived month), **and** a genuine multi-month range such as `1900-01`→`1900-02`. It is evaluated against the unfiltered `data.buckets`/`data.examples`/`data.accounts`, not the already-filtered `accounts`/`buckets` views, so it reflects the true archive state for that exact combination. Note: `selectedRangeGap` can be true even when the account has **positive lifetime posts** and the import is **fresh** — it only means that *this* selected period has no archived post. The `gapNote` copy is written to reflect that (see below).
- `src/components/reference/IntelligenceWorkspace.tsx:44` — `showGapNote = importStale || hasZeroPostAccount || selectedRangeGap` combines all three conditions.
- `src/components/reference/IntelligenceWorkspace.tsx:63` — the label is rendered conditionally inside the "Account coverage" (`health`) section: `{showGapNote&&<p className="intelligence-gap-note" role="status">{t('gapNote')}</p>}`.

This covers the scenarios named in the acceptance criteria plus the root-finding correction:
1. A selected person/platform with zero matching bucket/example across the selected month **or range** despite the account existing — surfaced via `selectedRangeGap`, which checks the exact person+platform against `data.buckets`/`data.examples` within the inclusive `[effectiveFrom, effectiveTo]` bounds while confirming the account row exists in `data.accounts`. This is an independent, selected-period reason: it can fire with positive lifetime posts and a fresh import, and covers explicit same-month, implicit-end, and multi-month selections alike.
2. `lastSocialImport` stale (>30 days) or missing — surfaced via `importStale`.
3. Any zero-post account in the current cohort/platform filter — surfaced via `hasZeroPostAccount` as a secondary, coarser signal independent of month selection.

Because the three triggers can each fire alone, the single shared `gapNote` string names all three as alternative ("or") reasons and uses conditional language, rather than asserting that the account is inactive.

## Limitations

- The "30 days" staleness threshold is a reasonable operational default chosen for this label; it is not pulled from an existing documented SLA elsewhere in the codebase, since no such constant exists prior to this change.
- This label is scoped to the "Account coverage" section only (where `accounts`, `lastSocialImport` are already in scope); it is not duplicated per month/row in the trend chart or table, since the acceptance criteria asks for a single visible label reacting to the combination of filters already applied.
- `selectedRangeGap` fires only when one person and one platform are selected and the inclusive resolved range `[effectiveFrom, effectiveTo]` contains no matching bucket/example for that person+platform despite the account existing. It intentionally does not fire for "all platforms"/"all people" views, since there the absence of a bucket for one platform-month pair among many is expected and not itself evidence of a collection gap. For a wide default window (no `from`/`to` set, resolving to the last 12 archived months) it fires only when that whole window is empty for the selected person+platform.
- `selectedRangeGap` reflects only the **selected period/range**, not lifetime activity: it can be true for an account with many lifetime posts and a fresh import when the selected period simply has no archived post. The copy therefore avoids any claim that the account is inactive.
- The staleness threshold is evaluated against `data.lastSocialImport` only; this label does not distinguish *why* an import is stale (collection failure vs. intentional pause), so operators must still consult the profile/collection pipeline before acting.
