# VPS product planning and quota balancing

Eric authorized moving planning to Hostinger, continuing the 42 remaining existing Orwell product steps, and swapping Claude/Codex responsibilities according to available subscription allocation.

The root controller refreshes native quota and readiness every minute without a model call. Paperclip wakes a planner only when the current product batch has finished or been safely quarantined. The planner runs on the VPS using the admitted provider with more available allocation. It proposes at most two whole existing product steps. A root validator checks the fixed 42-key authorization, exact product file paths, dependencies, and a finite verification vocabulary. The proposal cannot change budget, privileged commands, task checkmarks, credentials, avatars, or control-plane code.

Planning is not a second implementation team. Its proposal receives deterministic policy validation. Actual product work receives independent other-provider QA on an immutable source snapshot. Root acceptance still requires matching source revisions, actual contributor and reviewer sessions, durable native usage, meaningful product checks, successful publication and release evidence. A narrow sample cannot close a broader parent checkbox.

New implementation favors the provider with more usable percentage points, with three-point hysteresis. QA always uses the other provider from the recorded author. Repairs remain with the original author, even after the preferred provider changes. Sonnet/Luna are initial defaults. Claude can escalate to Opus after two documented QA rejections; Codex can escalate to Sol for a documented repair. Only one native model runs at a time.

The original allocation is unchanged: Codex baseline 22%, Claude baseline 0%, maximum 30 weekly percentage points per provider, with a three-point reserve. Original expiry remains October 16, 2026 at 3:50:25 p.m. Detroit time. Other chats count toward these account-wide deltas. Native meters are delayed admission signals, not provider-enforced project hard caps. A 45-second watchdog rechecks quota and user pause during a model turn. No API billing fallback is enabled.

Secondary capacity was raised from the earlier pilot limits to 192 runs, 100 million reported/observed tokens and eight million fresh tokens, because 42 tasks plus review exceed the original 64-run ceiling. The independent 12-runs-without-acceptance stop remains. These ceilings do not increase the original subscription allocation or expiry.

An unchanged failed plan waits 30 minutes; planning is capped at 24 turns per day. Blocked work is privately archived and restored to its earliest continuous pre-work baseline before another task can edit the checkout. Unsafe recovery stops visibly. Unknown native usage stops further spending. Missing source access remains blocked rather than falsely complete.

Frontend publication uses root-only native Vercel authentication, the fixed Orwell project and organization, an exact reviewed source commit, and independent API confirmation that the production alias points to the same READY deployment. Models do not receive deployment credentials. Chrome and Playwright on the VPS support actual live product checks.

Private runtime state lives under `/var/lib/orwell-agent-controller`; Paperclip bridge state under `/var/lib/orwell-paperclip`. The optional Mac UI tunnel is for viewing Paperclip, not execution. The former Mac planning heartbeat is paused. The public scoreboard remains available at https://orwell-panama.vercel.app/scoreboard#live-operations.

Planning may stop with unfinished items if the original deadline, budget reserve, prerequisite, recovery or QA guard prevents safe completion. That is reported as held or blocked, never as a finished backlog.
